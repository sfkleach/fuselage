# Task: Implement uv-bundle — orchestrate Python packaging into a fuselage self-executing bundle

## Overview

`uv-bundle` is a high-level orchestration tool that automates the complete
workflow for packaging a Python project (managed by `uv`) into a self-executing
ELF binary. It sequences four tools — `fuselage --dynamic-empty`, `uv sync`,
`mksquashfs`, and `fuselage-bundle` — that the user would otherwise have to
coordinate by hand.

## Cargo changes

### New dependency

Add `toml = "0.8"` to `[dependencies]` in `Cargo.toml`. This is used to read
`pyproject.toml` and extract the package name (used to derive the fixed mount
path `/run/fuselage/<name>`) and, optionally, the default script entry point.

### New [[bin]] entry

```toml
[[bin]]
name = "uv-bundle"
path = "src/bin/uv_bundle.rs"
```

## Invocation

```
uv-bundle --project=DIR --output=BINARY [OPTIONS]
```

| Flag | Description |
|---|---|
| `--project=DIR` | Directory containing `pyproject.toml` (required). |
| `--output=BINARY` | Path for the produced self-executing ELF binary (required). |
| `--module=MOD` | Python module to run with `-m MOD`. Defaults to the package name from `pyproject.toml`. |
| `--dev` | Include dev dependencies in the bundle. Default is `--no-dev` (excluded). |
| `--squashfs=PATH` | Keep the intermediate squashfs at this path instead of a temp file. |
| `--uv-arg=ARG` | Extra argument forwarded to `uv sync` (repeatable). |

## Pipeline

The four steps run in order:

### Step 1 — `fuselage --dynamic-empty`

Creates an empty private tmpfs at `/run/fuselage/<name>`. The subsequent steps
run inside this ephemeral mount. Once the fuselage invocation exits, the mount
is automatically cleaned up by the kernel.

### Step 2 — `uv sync`

Installs the project's dependencies into a `.venv` inside the mount:

```bash
UV_PROJECT_ENVIRONMENT=/run/fuselage/<name>/.venv \
  uv sync --project <project-dir> [--extra-uv-args]
```

Setting `UV_PROJECT_ENVIRONMENT` redirects the venv into the mount point so it
is included in the squashfs image.

### Step 3 — `mksquashfs`

Compresses the populated mount directory into a squashfs archive:

```bash
mksquashfs /run/fuselage/<name> <squashfs-path> -noappend -quiet
```

The squashfs file is written to a temp path (or to `--squashfs` if supplied)
outside the mount so that it survives after the mount is torn down.

### Step 4 — `fuselage-bundle`

Packs the squashfs and the baked-in fuselage invocation into the output binary:

```bash
fuselage-bundle \
  --archive=<squashfs-path> \
  --output=<output> \
  -- \
  --static=/run/fuselage/<name>:/proc/self/exe \
  --run /run/fuselage/<name>/.venv/bin/python \
  -- -m <module>
```

## Implementation notes

Steps 1–3 must run as a single `fuselage` invocation so that `uv sync` and
`mksquashfs` share the same mount namespace. The simplest implementation spawns:

```bash
fuselage --dynamic-empty=/run/fuselage/<name> -- sh -c '<uv-cmd> && <mksquashfs-cmd>'
```

`sh -c` is used to chain the two commands inside the mount namespace without
requiring a separate wrapper binary.

Step 4 spawns `fuselage-bundle` as a normal child process after the fuselage
mount has been torn down — it operates on the squashfs file, not the mount.

## Example

```bash
uv-bundle --project ~/src/myapp --output ~/bin/myapp
# Produces ~/bin/myapp, a self-executing ELF that:
#   1. Mounts its embedded squashfs at /run/fuselage/myapp
#   2. Runs /run/fuselage/myapp/.venv/bin/python -m myapp [ARGS...]
```
